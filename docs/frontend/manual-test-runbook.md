## 1. 环境准备

### 1.1 依赖与目录

| 项 | 要求 |
| --- | --- |
| Python | 3.10+（仓库 `.venv` 可直接用），已装 `requirement.txt` |
| Node.js | 18+，已执行 `npm install`（`frontend/node_modules` 存在） |
| 浏览器 | Chrome / Edge 最新版；建议开一个无痕窗口，便于验证「无本地登录态」场景 |
| 工作目录 | 后端命令在仓库根目录执行；前端命令在 `frontend/` 执行 |

### 1.2 后端环境变量

在启动后端的终端里设置（PowerShell 写法）：

```powershell
$env:AUTH_SECRET_KEY='至少32个字符的随机串-请自行替换-0123456789'
$env:DEEPSEEK_API_KEY='你的DeepSeekKey'      # 会话聊天用例需要真实值
$env:DASHSCOPE_API_KEY='你的DashScopeKey'    # 知识库上传/检索用例需要真实值
$env:QDRANT_URL='http://127.0.0.1:6333'      # 知识库检索需要 Qdrant 在跑
# 建议用独立测试库，避免污染仓库根目录的 chat_history.db
$env:CHAT_DB_PATH="$PWD\manual-test.db"
$env:LANGGRAPH_CHECKPOINT_DB_PATH="$PWD\manual-test-checkpoint.db"
# 可选：仅在需要用「直连后端」（不走 Vite 代理）验证 CORS 时才需要
$env:CORS_ALLOW_ORIGINS='http://127.0.0.1:5173,http://localhost:5173'
```

> 已验证事实：`DEEPSEEK_API_KEY` / `DASHSCOPE_API_KEY` 只给占位值时**后端仍能正常启动**
> （知识库集合初始化被推迟到首次使用），但一旦真的发聊天或上传文档就会失败。
> 所以「只测界面不测聊天」时可以先用占位值跑通前几个模块。

### 1.3 启动命令

```powershell
# 终端 1：后端（仓库根目录）
python -m uvicorn main:app --host 127.0.0.1 --port 8000

# 终端 2：前端（frontend/ 目录）
npm run dev
```

前端地址固定为 <http://127.0.0.1:5173>（`vite.config.ts` 中 `host:127.0.0.1`、`port:5173`），
所有 `/api` 请求由 Vite 代理转发到 `http://127.0.0.1:8000` 并去掉 `/api` 前缀。

### 1.4 可选：灌入演示业务数据（审批/退款用例需要）

审批中心要有东西可看，必须先有订单。Seeder 会为指定企业生成 2 个客户、3 个订单、
2 条物流、2 个工单（幂等，可重复执行）：

```powershell
# 先注册并登录一个账号、创建一个企业，然后取两个 id：
#   用户 id  <- GET /auth/me         （或浏览器里 F12 看 /auth/me 响应）
#   企业 id  <- GET /organizations/
python -m app.demo_data.cli `
  --database-path .\manual-test.db `
  --organization-id "<上一步的企业 id>" `
  --actor-user-id "<上一步的用户 id>"
```

可用的订单号（聊天里直接问这几个）：

| 订单号 | 状态 | 适合问什么 |
| --- | --- | --- |
| `ORD-DELAY-001` | processing（未发货） | 超过承诺时间仍未发货 → 容易触发补偿提案 |
| `ORD-TRANSIT-001` | shipped / in_transit | 查询运输进度 |
| `ORD-DELIVERED-001` | delivered / 已签收 | 签收后商品破损 → 容易触发退款提案 |

> `manual-test.db` 与 `manual-test-checkpoint.db` 请加入本地忽略或测试后删除；
> 不要提交到仓库。

## 3. A 环境与启动

### A-01 后端可访问

- **前置条件**：后端已按 1.3 启动，终端无 `Traceback`。
- **操作步骤**：浏览器打开 <http://127.0.0.1:8000/docs>。
- **预期结果**：出现 Swagger UI 接口文档页，标题为 `FastAPI`；能看到 **9 个**
  分组标签（**不叫** `conversations` / `approvals`）：
  `knowledge`、`authentication`、`organizations`、`退款/补偿审批与Run`、
  `创建新会话`、`设置会话的系统提示词`、`查询会话列表`、`查询会话历史消息`、
  `向模型聊天`。
  - 会话与审批接口用的是**中文标签**（仅 `knowledge`/`authentication`/
    `organizations` 为英文）；
  - **不应出现 `default` 分组**（原 `PUT /conversations/{id}/system-prompt/`
    未声明 `tags` 会落入 `default`，见 DEF-05，已修复）。

### A-02 接口数量核对

- **前置条件**：A-01 通过。
- **操作步骤**：在 Swagger 页面顶部搜索框依次搜索 `members`、`action-runs`。
- **预期结果**：
  - 出现 `GET /organizations/{organization_id}/members/`、
    `PATCH /organizations/{organization_id}/members/{user_id}/`、
    `DELETE /organizations/{organization_id}/members/{user_id}/` 三条；
  - 出现 `GET /action-runs/{run_id}/` 与 `POST /action-runs/{run_id}/resume/`；
  - 全站路径数为 **22**、操作数为 **27**（新增
    `GET /knowledge/documents/{id}/versions/{id}/content/` 正文接口后）。
    （本文档此前误写为「路径数 23」——23 是 `42b83d9` 时的**操作数**，
    见 `api-inventory.md` 勘误与 DEF-04。可直接用
    `python -c "import main; print(len(main.app.openapi()['paths']))"` 复核；
    正文接口前为 21 路径 / 26 操作。）

### A-03 前端页面可访问

- **前置条件**：前端 `npm run dev` 已启动且终端打印 `Local: http://127.0.0.1:5173/`。
- **操作步骤**：打开 <http://127.0.0.1:5173>。
- **预期结果**：页面跳转到 `/login`，显示标题 **「登录」** 与副标题
  **「欢迎回来，请登录你的 SupportPilot 账号」**；页面无控制台红色报错
  （F12 Console 中不含 `Uncaught`）。

### A-04 未登录访问受保护页面被拦截

- **前置条件**：浏览器处于**无痕窗口**（无本地登录态）。
- **操作步骤**：直接访问 <http://127.0.0.1:5173/app/members>。
- **预期结果**：被重定向到 `/login`，**地址栏 query 中带 `redirect=/app/members`**；
  登录成功后应回到成员管理页（见 B-08）。

### A-05 未知路径回落

- **前置条件**：同上。
- **操作步骤**：访问 <http://127.0.0.1:5173/not-exist-page>。
- **预期结果**：不发生白屏或 404 页面；路由回落（未登录 → 登录页；已登录且有企业
  → 工作台）。

### A-06 前端请求确实带代理前缀

- **前置条件**：前端已启动，打开 F12 → Network。
- **操作步骤**：访问 `/login`，随便提交一次登录（可填错误密码）。
- **预期结果**：Network 中该请求 URL 为 **`/api/auth/login`**（同源、5173 端口），
  状态码 401；不存在指向 `8000` 端口的失败请求，也不存在 CORS 报错。

### A-07 外部服务缺失时的降级表现（🔑）

- **前置条件**：`DEEPSEEK_API_KEY` 或 `DASHSCOPE_API_KEY` 为占位值，或 Qdrant 未启动。
- **操作步骤**：登录后进入会话页，发送任意问题（例如「你好」）。
- **预期结果**：页面不会白屏；消息气泡显示失败态（`data-test="agent-failed"`，
  带 `role="alert"`），输入框恢复可用；**不会**出现伪造的 Agent 回答或伪造的知识引用。

### A-08 真实 CORS 响应头（可选，直连场景）

- **前置条件**：后端已启动。
- **操作步骤（命令行，无需浏览器）**：

  ```powershell
  curl.exe -i -X OPTIONS http://127.0.0.1:8000/organizations/ `
    -H "Origin: http://127.0.0.1:5173" `
    -H "Access-Control-Request-Method: POST" `
    -H "Access-Control-Request-Headers: authorization,x-organization-id"
  ```

- **预期结果**：状态 **200**；响应头含
  `access-control-allow-origin: http://127.0.0.1:5173`、
  `access-control-allow-headers` 中包含 **`X-Organization-ID`**、
  `access-control-allow-methods` 含 `GET, POST, PUT, PATCH, DELETE, OPTIONS`、
  `access-control-max-age: 600`。
  （本会话已实测通过，可直接对照。）

## 4. B 认证与登录态

### B-01 注册新账号成功

- **前置条件**：无痕窗口，处于登录页。
- **操作步骤**：
  1. 点击页面下方 **「创建账号」**；
  2. 用户名填 `tester01`，密码填 `Test1234`，确认密码填 `Test1234`；
  3. 提交。
- **预期结果**：提示注册成功并**跳到登录页**（注册成功后不自动登录，这是后端既定行为）；
  用 `tester01 / Test1234` 登录可成功。

### B-02 注册用户名非法被前端拦截

- **前置条件**：处于注册页。
- **操作步骤**：用户名填 `Ab`（含大写且不足 3 位），密码 `Test1234`，确认密码一致，提交。
- **预期结果**：表单下方出现中文校验错误，文案为
  **「用户名须为 3–32 位小写字母、数字或下划线」**；**不发出网络请求**（Network 无记录）。

### B-03 注册用户名已存在（服务端 409）

- **前置条件**：`tester01` 已注册。
- **操作步骤**：再用 `tester01` 注册一次（大小写可写成 `TESTER01` 验证不区分大小写）。
- **预期结果**：提示 **「用户名已被注册」**；页面停留在注册页，不清空已填内容。

### B-04 密码长度边界

- **前置条件**：处于注册页，用户名 `tester02`（未注册）。
- **操作步骤**：密码填 `Test123`（7 位）→ 提交；再改成 8 位 `Test1234` → 提交。
- **预期结果**：7 位时被前端拦截或提示
  **「密码长度须为 8–72 个字符」**，不发请求；8 位时注册成功。

### B-05 两次密码不一致

- **前置条件**：处于注册页。
- **操作步骤**：密码 `Test1234`，确认密码 `Test12345`，提交。
- **预期结果**：提示两次密码不一致（中文），不发出请求。

### B-06 登录密码错误

- **前置条件**：`tester01` 已注册，处于登录页。
- **操作步骤**：用户名 `tester01`，密码 `WrongPass1`，提交。
- **预期结果**：提示 **「用户名或密码错误」**（后端对「用户不存在」与「密码错误」
  返回完全一致的文案，这是防枚举设计）；停留在登录页。

### B-07 登录成功并落地工作台

- **前置条件**：`tester01` 已注册且**至少有一个企业**（若没有，先做 C-01）。
- **操作步骤**：用户名 `tester01`，密码 `Test1234`，提交。
- **预期结果**：进入 `/app` 工作台；顶部显示用户名 `tester01` 与角色标签；
  左侧「功能模块」菜单列出 **工作台 / 客服对话 / 审批中心 / 知识库 / 成员管理** 五项，
  且**没有**「（待实现）」字样、也没有灰色禁用项。

### B-08 刷新页面恢复登录态

- **前置条件**：B-07 已登录。
- **操作步骤**：按 F5 刷新页面。
- **预期结果**：不闪回登录页；仍停留在 `/app`，用户名与当前企业保持不变
  （刷新期间调用了 `/auth/me` 做登录态恢复）。

### B-09 ⚠️ 退出登录

- **前置条件**：已登录。
- **操作步骤**：点击顶栏右上角 **「退出登录」**。
- **预期结果**：弹出确认框；确认后回到登录页并提示已退出登录。
  再次点浏览器「后退」**不应**恢复出工作台内容（本地登录态已清空，守卫会再次拦回登录页）。

## 5. C 企业与租户上下文

### C-01 创建第一个企业

- **前置条件**：`tester01` 已登录，且**没有任何企业**（新账号即是）。
- **操作步骤**：
  1. 登录后被引导到 `/organizations`；
  2. 点击 **「创建企业」**；
  3. 企业名称填 `测试企业A`，提交。
- **预期结果**：提示企业创建成功并自动进入 `/app`；顶栏企业切换器显示 `测试企业A`；
  角色标签显示 **管理员**（创建者自动成为 admin）。

### C-02 企业名称长度校验

- **前置条件**：处于企业选择页。
- **操作步骤**：在创建企业对话框里输入单字 `A`，提交。
- **预期结果**：提示 **「企业名称长度须为 2–100 个字符」**；不发出请求。

### C-03 企业列表与角色展示

- **前置条件**：`tester01` 拥有 `测试企业A`（admin）。
- **操作步骤**：点击顶栏 **「全部企业」**（或左侧「选择企业」入口）进入 `/organizations`。
- **预期结果**：卡片列表展示 `测试企业A` 与文案「我在该企业的角色：管理员」，
  右侧有「进入 →」；页面无虚构的统计数据。

### C-04 顶栏切换企业

- **前置条件**：至少有两个企业（可再创建 `测试企业B`，或用 D-01 把他人加进来）。
- **操作步骤**：点击顶栏企业切换器（按钮显示当前企业名）→ 在下拉中选择另一个企业。
- **预期结果**：提示 **「已切换到「<企业名>」」**；顶栏名称更新；
  页面数据按新企业重新加载（切到没有数据的企业应看到各自空态，**不应**残留上一个
  企业的列表内容）。

### C-05 刷新后保持企业选择

- **前置条件**：已切换过企业。
- **操作步骤**：F5 刷新。
- **预期结果**：当前企业保持为刷新前选择的那一个，不回退到第一个企业。

### C-06 失去企业权限后自动失效（依赖 D-08）

- **前置条件**：`tester02` 已被 `tester01` 加入 `测试企业A`，且 `tester02` 当前正选中该企业。
- **操作步骤**：`tester01` 在成员管理页把 `tester02` 移除（D-08）；然后在 `tester02`
  的浏览器里刷新页面。
- **预期结果**：`tester02` 的企业列表不再包含 `测试企业A`，被引导回企业选择页；
  本地保存的企业选择被清除，**不会**继续带着已失效企业发租户请求。

### C-07 无企业用户被挡在工作台外

- **前置条件**：注册一个新账号 `tester09`（未加入任何企业）。
- **操作步骤**：用 `tester09` 登录后，直接访问 <http://127.0.0.1:5173/app/chat>。
- **预期结果**：被改道到 `/organizations`，并提示先创建或加入企业；
  不会出现空白工作台或持续转圈。

### C-08 窄屏布局

- **前置条件**：已登录进入 `/app`。
- **操作步骤**：F12 切换设备工具栏，宽度设为 375px（iPhone 尺寸）。
- **预期结果**：左侧导航自动隐藏，顶栏保留核心操作；页面无横向滚动条，
  文字不被裁切。

## 6. D 成员管理

> 前置：`tester01`（admin）与 `tester02`（普通账号）都已注册；`测试企业A` 存在。
> 建议在本模块开始前，用 `tester01` 登录并进入 `测试企业A`。

### D-01 添加成员成功

- **前置条件**：`tester02` **已注册**但不在 `测试企业A`。
- **操作步骤**：
  1. 左侧菜单点击 **「成员管理」**；
  2. 点击右上 **「添加成员」**；
  3. 用户名填 `tester02`，角色选 **客服**，点击 **「添加」**。
- **预期结果**：提示已添加成员；列表新增一行 `tester02`，角色显示 **客服**，
  并显示「加入时间：YYYY-MM-DD HH:mm」；页头「共 N 位成员」数字 +1。

### D-02 添加自己要加入的成员（已在企业中）

- **前置条件**：D-01 已完成。
- **操作步骤**：再次添加 `tester02`（角色任选）。
- **预期结果**：对话框内提示 **「该用户已是本企业成员」**；列表不出现重复行。

### D-03 添加不存在的用户

## 8. F 知识库

> 前置：以 **admin** 身份进入企业（知识库写操作仅管理员）。

> UTF-8 非空文本。仓库里现成的 `TestWordDocuments/1-招聘录用制度.docx` 属于
> **Word 文档，HTTP 路由层会直接拒绝**，正好可用于 F-04 的负例。
> 请先在桌面新建一个文本文件，例如 `售后政策.md`，内容：
> `# 售后政策\n\n## 到货破损\n\n签收后 7 天内发现破损，可申请全额退款或优惠券补偿。`

### F-01 ⚠️🔑 上传新文档

  1. 左侧点击 **「知识库」**；
  2. 点击 **「上传文档」**；

  **页面自动跳转到该文档详情页**（内容重复或未成功时不跳转，回执留在列表查看）；
  新文档状态为 **已启用**，来源类型 **Markdown**；
  详情页可见版本 `v1` 为当前有效版本、入库任务状态为 **成功**。

### F-02 上传完成但内容重复（幂等）

> ⚠️ **入口更正（DEF-07）**：去重是**「文档内版本维度」**的，只在
> **「上传新版本」**入口生效（`app/knowledge/ingestion.py::_resolve_duplicate`
> 以 `document_id` 为查询范围，配合 `(org, document_id, content_hash)` 唯一约束）。
> **「上传文档」入口不做去重**：同一内容会作为**新文档**创建（201），
> 并可与原文档**同时参与检索**。本文档原文把入口写成了「上传文档」，有误。

- **前置条件**：F-01 已完成，且该文档详情页为 admin 视角。
- **操作步骤**：进入该文档**详情页** → 点击 **「上传新版本」** →
  选择与当前有效版本**完全相同内容**的同名文件 → 在确认步骤提交。
- **预期结果**：提示 **「上传内容与当前有效版本相同，未创建重复版本。」**；
  文档的**版本历史不新增**条目（版本号不变）。

#### F-02b 反例：「上传文档」入口不做跨文档去重（已知行为）

- **前置条件**：同 F-02。
- **操作步骤**：回到知识库**列表页**，从 **「上传文档」** 入口再次上传
  **完全相同内容**的同名文件。
- **预期结果**：**201 且创建了一篇新文档**（新 `document_id`），列表文档数 +1；
  **不会**提示「内容与当前有效版本相同」。
- **产品风险（建议确认，非本次修复项）**：同一内容的重复文档会**同时参与检索**，
  若两份内容互相矛盾（例如「签收后 7 天」与「签收后 15 天」两版政策），
  会污染检索证据质量，使 Agent 判定**证据不足**而拒绝回答
  （见 E-07 实测）。是否需要在该入口增加内容级提示，待产品侧确认。

- **操作步骤**：点击 **「上传新版本」** → 选择文件 → 在确认步骤点击提交。
- **预期结果**：版本号递增（`v2`），新版本成为**当前有效版本**；历史版本仍保留；
  确认前不发送请求（可先返回修改验证）。

### F-11 ⚠️ 停用与启用

- **前置条件**：admin；文档当前状态为 **已启用**。
- **操作步骤**：点击 **「停用」** → 确认；随后点击 **「启用」** → 确认。
- **预期结果**：停用后状态变为 **已停用**，按钮切换为「启用」；
  启用后恢复 **已启用**；确认弹窗在点「取消」时不发请求。
  对 **处理中/失败** 状态的文档**不出现**直接启用/停用入口。

### F-12 入库任务错误查询

- **前置条件**：有一篇上传失败或状态不确定的文档（可用 F-05 的失败回执）。
- **操作步骤**：在详情页查看 **入库任务** 面板。
- **预期结果**：展示任务状态（**排队中 / 处理中 / 成功 / 失败**）、尝试次数，
  失败时展示错误码与错误消息；无任务时显示明确空态文案而不是空白。

### F-13 agent 只读视图

- **前置条件**：`tester02` 为客服角色且在当前企业。
- **操作步骤**：用 `tester02` 登录进入知识库列表与详情。
- **预期结果**：能浏览文档；页面显示只读说明；
  **看不到**「上传文档」「上传新版本」「停用」「启用」按钮。
  （**「查看正文」按钮对 agent 同样可用**：正文读取是读接口，见 F-14-1。）

### F-14 🔑 正文查看与引用跳转

> 覆盖设计稿 `docs/superpowers/specs/2026-09-09-knowledge-document-content-viewer-design.md`
> 的阶段 B 交付。前置：F-01 已入库一篇文档（建议同时准备一份 `.docx` 或 `.pdf`
> 文档，以及一份改过内容、有多个版本的文档）；E-07 已拿到带引用的回答。
> 所有跳转都用**结构化字段**（回答文本里的 `[C1]` 只用于定位引用卡片）。

#### F-14-1 成员可读正文（agent 与 admin 均可）

- **操作步骤**：进入某文档详情页 → 点击 **「查看正文」**。
- **预期结果**：弹窗内展示正文（Markdown 渲染：标题/列表/表格/代码块正常排版，
  **不是** `#`、`**` 之类的语法源码）；头部显示文档标题与
  **「版本 v1 · 正文 26 字符」**（形如 `版本 vN · 正文 M 字符`）;
  有标题的文档在正文上方展示**目录**，点击目录项滚动到对应章节；
  正文加载失败时弹窗内出现错误与 **「重试」** 按钮，详情页本身不受影响。
  用 `tester02`（客服）重复一次，结果应完全一致。

#### F-14-2 跨租户不可读（需两个企业）

- **前置条件**：账号同时属于**两个**企业（见 C-01/C-04），且只有企业 A 有知识库文档。
- **操作步骤**：
  1. 在企业 A 打开对话，拿到一条引用的 `documentId`（或直接记下详情页 URL 中的文档 ID）；
  2. 顶栏切到企业 B，在地址栏直接访问 `/app/knowledge/<企业A的文档ID>`。
- **预期结果**：页面回到知识库列表并提示 **「文档不存在或已不可访问」**；
  正文接口返回 **404 `DOCUMENT_NOT_FOUND`**；
  **响应体里不含标题、正文、版本号等任何企业 A 的信息**（Network 面板核对）。
  不区分「不存在」与「不属于你」是刻意的防枚举口径。

#### F-14-3 历史版本提示（引用版本 ≠ 当前有效版本）

- **前置条件**：一篇文档有 ≥2 个版本（F-10 上传过新版本）。
- **操作步骤**：
  1. 先对 v1 的内容提问拿到引用（或在 v1 时提问并保留该回答）；
  2. 上传 v2 使其成为当前有效版本；
  3. 回到那条回答，点击该引用的 **「查看原文位置」**。
- **预期结果**：面板/弹窗中显示 **「该引用来自历史版本 vN，当前有效版本为 vM」**
  两个版本号都要出现；正文是 **v1 的内容**（读的是引用所属版本，不是当前有效版本）；
  引用片段被高亮并滚动到可见位置。

#### F-14-4 PDF / Word 正文（原「转换提示」已于 2026-09-16 移除）

- **前置条件**：F-01 上传的是 `.docx` 或 `.pdf`。
- **操作步骤**：打开该文档正文（详情页「查看正文」或从引用跳转）。
- **预期结果**：正文正常渲染为入库时转换后的 Markdown，**不是** PDF/Word 原文排版；
  正文上方**不再出现**任何「由 PDF/Word 自动转换」提示——该提示已按产品决定移除，
  若再次出现即为回归（前端回归测试守着「不再出现」）。

#### F-14-5 偏移为空时降级（不阻断打开）

- **前置条件**：能拿到一条 `start_offset`/`end_offset` 为 `null` 的引用
  （后端允许偏移为空；此类引用可能来自历史载荷或降级情形）。
- **操作步骤**：点击该引用的入口。
- **预期结果**：入口文案为 **「查看来源文档」**（而不是「查看原文位置」）；
  点击后正文正常打开，显示
  **「该引用未记录精确位置，已为你打开来源文档」**；
  若引用带章节路径则滚动到对应章节，否则停在正文顶部；**不高亮任何片段**，
  也不报错。注意：偏移 **0 是合法值**（片段在正文开头），必须仍按「可精确定位」处理。

#### F-14-6 停用文档仍可读正文

- **操作步骤**：admin 在详情页 **停用**该文档（F-11）→ 再打开其正文。
- **预期结果**：正文**仍然可读**；页面上出现
  **「该文档已停用，不再参与新的知识检索」**；
  它不再出现在新的检索召回里（这与「历史引用仍能核对来源」是一致的）。

#### F-14-7 引用跳转：桌面同屏 / 窄屏整页

- **前置条件**：浏览器窗口可调宽窄；已有一条带偏移的引用（E-07）。
- **操作步骤**：
  1. 窗口宽度 **≥1280px**，点击引用的 **「查看原文位置」**；
  2. 再点击**另一条**引用；然后点面板右上角 **「关闭」**；
  3. 把窗口缩到 **<1280px**，再次点击引用。
- **预期结果**：
  - 第 1 步：**右侧出现正文面板并与对话区同屏并排**（不是盖住对话的遮罩）；
    对话区自动收窄但消息不重排、输入框仍可用；引用片段被高亮；
    面板打开时**对话区不滚动**（阅读位置不变）；
  - 第 2 步：切换引用只**重新定位**（同版本**不重复请求**正文，可在 Network 核对）；
    关闭面板后对话区恢复原宽，**会话不重载、消息不丢失、滚动位置保持**；
  - 第 3 步：窄屏**不并排**，改为整页跳到
    `/app/knowledge/<文档ID>?versionId=…&start=…&end=…` 并自动打开该版本、定位高亮；
    可用浏览器后退或页面上的「返回知识库」回到列表。

#### F-14-8 正文失败不影响对话

- **操作步骤**：在对话页打开一条引用 → 断开后端（或让正文接口失败）→ 观察。
- **预期结果**：**面板内**显示错误与「重试」按钮；
  **对话区完全不受影响**——回答与引用卡片都还在，可以继续对话；
  恢复后端后点「重试」能正常加载正文。

#### F-14-9 已知限制：刷新后引用消失

- **操作步骤**：拿到带引用的回答后 **F5 刷新**页面。
- **预期结果**：**问答文本被恢复，但引用卡片与「查看原文位置」入口消失**
  （后端历史接口只保存安全问答文本，不返回 `citations`，前端不伪造）。
  刷新后**无法**从历史跳转正文——这是**已知限制**（设计稿 §6 backlog：
  引用在会话历史中持久化），**不要当 Bug 上报**。

> 同一（文档、版本）内多次跳转只请求一次正文，缓存范围是**内存 + 会话内**，
> **不写 localStorage**；切换企业或退出登录时缓存与面板一并清理。

## 10. H 跨模块与安全边界

### H-01 跨企业数据不可见

- **前置条件**：`tester01` 有 `测试企业A`，另有一个账号有 `测试企业B`。
- **操作步骤**：把 `测试企业A` 的某个审批/文档 ID 记下，切换到 `测试企业B` 后，
  在地址栏直接访问该 ID 的详情页（例如 `/app/knowledge/<A的文档id>`）。
- **预期结果**：提示资源不存在或已被移除（后端统一伪装 404），
  **不泄露**该资源在另一个企业的标题或内容。

### H-02 401 会话过期统一处理（可选，需改配置）

- **前置条件**：把后端 `ACCESS_TOKEN_TTL_SECONDS` 设为较小值（如 `60`）后重启，
  然后重新登录。
- **操作步骤**：登录后等待超过该时长，分两条路径各验一次：
  1. **服务端 401 路径**：停留在页面内，点击任意页面操作（如切到知识库）；
  2. **本地判定过期路径**：不点击任何按钮，直接 **F5 刷新页面**，
     或地址栏直接输入受保护路由（如 `/app/knowledge`）。
- **预期结果**：两条路径**都要**清除本地登录态、跳回登录页并提示
  「登录已过期，请重新登录」；不会无限转圈或反复报错。
  - 路径 1：跳转 URL 为 `/login?reason=expired`；
  - 路径 2（DEF-03，已修复）：跳转 URL 为
    **`/login?redirect=/app/knowledge&reason=expired`**（同时保留原始目标）。
    修复前该路径**不带 `reason`**，用户刷新后被踢回登录页却得不到任何解释。
  - 反向校验：**主动点「退出登录」**不属于过期，回到登录页时
    **不应**出现「登录已过期」提示。

### H-03 规则：管理员不能自我降级/自我移除（后端强制）

- **前置条件**：`tester01` 是 `测试企业A` 唯一管理员。
- **操作步骤**：
  1. 界面上确认己方行没有改角色/移除入口（D-07）；
  2. 用命令行直接调用后端接口尝试自我操作（绕过界面）：

     ```powershell
     curl.exe -i -X PATCH "http://127.0.0.1:8000/organizations/<企业id>/members/<自己的userid>/" `
       -H "Authorization: Bearer <自己的token>" `
       -H "Content-Type: application/json" `
       -d "{\"role\":\"agent\"}"
     ```

- **预期结果**：返回 **409**，detail 为
  `administrators cannot change their own role`（删除自己则返回
  `administrators cannot remove their own membership`）；
  企业里**始终保留至少一名管理员**。

### H-04 规则：界面隐藏不是安全边界

- **前置条件**：`tester02` 为客服。
- **操作步骤**：用 `tester02` 的 token 直接调用需要 admin 的接口，例如
  上传文档或作出审批决定。
- **预期结果**：后端返回 **403**（管理类）或 **404**（非成员），
  前端即使隐藏了按钮也无法绕过；这验证「前端隐藏 + 后端强制」双保险。

### H-05 同企业成员可见性口径

- **前置条件**：`tester01`、`tester02` 同属 `测试企业A`。
- **操作步骤**：分别查看审批列表。
- **预期结果**：审批列表是**企业级**的（同企业成员都能看到彼此企业内的审批）；
  而**会话列表是用户级**的（`tester01` 看不到 `tester02` 的会话）。

### H-06 时间与时区展示

- **前置条件**：已有数据（成员加入时间、审批创建时间、消息时间）。
- **操作步骤**：对比页面显示时间与浏览器本地时间/实际操作时间。
- **预期结果**：时间均按**本地时区**展示且与操作时刻一致（后端存 UTC，前端统一换算）；
  无「差 8 小时」现象；空值显示 **「—」**。
  - 重点核对**审批详情页**：基本信息「创建时间」、请求版本「创建时间」、
    版本历史每条的版本时间、决定摘要「决定时间」、Run 状态面板的
    「创建/更新时间/完成时间」——这些字段曾直接透出后端 UTC ISO 文本
    （如 `2026-09-11T02:21:32Z`，比本地早 8 小时），见 DEF-01，已修复。
  - 同一时刻应在这几处得到**一致**的本地时间文本（`YYYY-MM-DD HH:mm`），
    并与审批**列表**页、**成员管理**页的口径一致。

### H-07 金额展示

- **前置条件**：存在一条金额为整分/分的审批（如 12345 分）。
- **操作步骤**：观察审批列表与详情的金额。
- **预期结果**：显示为 **`¥123.45`** 形式（两位小数、千分位可选），
  与请求版本金额一致；不存在浮点误差导致的 `123.45000000001` 之类显示。

## 11. 已知边界与不测项（避免误判为缺陷）

以下均为**后端当前没有的能力**，界面已如实处理（不提供入口、不伪造数据），
请不要当作 Bug 上报：

1. **无会话删除/重命名/归档**：会话只能在「新会话」时给系统提示词，标题由首条消息自动推导。
2. **无成员移除自己/退出企业、无转让管理员、无修改企业名**：管理员自我移除被 409 禁止。
3. **无知识库文档删除、无列表分页与搜索参数**：搜索/筛选/排序全在前端本地做；
   删除能力只有「停用」。**正文查看已提供**（按版本读取入库时转换后的 Markdown，
  见 F-14），但**仍无原文下载**——读到的是转换后的 Markdown，不是 PDF/Word 原件。
4. **无「待我审批」数量汇总接口**：审批待办数字只能靠列表长度推断（本页未展示总数）。
5. **无用户→用户名反查接口**：审批/提案里的 `*_by_user_id` 只能显示 ID，不显示用户名。
6. **无服务端登出/吊销 Token**：退出登录只清本地状态，Token 只能自然过期。
7. **无流式/SSE/WebSocket**：聊天是同步请求，可能持续数十秒；超时后**不会自动重试**，
   界面会提示「结果状态可能不确定，请刷新历史后确认」——这是设计而非卡死。
8. **`.docx` 无法上传**：领域层支持 Word，但 HTTP 路由层当前只接受 `.md/.markdown/.txt`。
9. **跨企业一律 404**：不会区分「不存在」与「不属于你」，这是刻意的防枚举设计。
10. **无成员数/文档数汇总接口**：页面上的「共 N 位成员」「共 N 篇文档」都是列表长度。
11. **「上传文档」入口不做跨文档内容去重**：同一内容会被创建成**独立文档**并
    同时参与检索；去重只发生在**同一文档内**的「上传新版本」入口
    （详见 F-02 与 F-02b）。是否会污染检索证据质量属**待产品确认**项，
    当前行为与实现一致，**不要当作 Bug 上报**。
12. **管理员在界面上不可降级为客服**：成员一旦成为管理员，其行的角色下拉即被
    禁用，只能「移除」不能降级（详见 D-05/D-06 与 DEF-06）。
13. **会话系统提示词无「清空」入口**：接口要求 `system_prompt` strip 后非空
    （空值 → 422），因此设置后无法通过界面改回「未设置」，只能覆盖为新的非空文本。
14. **检索摘要的证据状态原样透出英文枚举**（如 `insufficient`），
    这是与 E-08 审批状态一致的既定口径（详见 E-07 与 DEF-08）。
15. **刷新后引用消失**：聊天历史接口不返回 `citations`，因此刷新页面后引用卡片
    与「查看原文位置」入口都会消失（正文查看本身不受影响，可从知识库进入）。
    属设计稿 §6 的 backlog，**不是缺陷**（详见 F-14-9）。
16. **正文不做分页**：正文接口一次返回全文（上传上限 2 MiB，纯中文约 70 万字符）；
    高亮定位只做一次 DOM 遍历，滚动/缩放不会重复遍历。文档极大时首次渲染会稍慢，
    属当前既定取舍（设计稿 §6 已登记窗口化 backlog）。
17. **正文渲染的是 Markdown 而非原文排版**：引用跳转天然指向入库时那份 Markdown，
    PDF/Word 的原始版式不还原；查看器**不再**为此上屏提示（2026-09-16 产品决定，
    见 F-14-4）。

**发现问题时的定位建议**：

1. 先看 F12 → **Console** 是否有 `Uncaught` 报错（前端异常）；
2. 再看 F12 → **Network** 中该请求的**状态码与响应体**：
   - `422` → 请求体/参数不符合契约（属输入或契约问题）；
   - `400 organization context required` → 缺少企业上下文（未选企业）；
   - `403 admin role required` → 角色不足（预期行为）；
   - `404` → 资源不存在或不属于当前企业（防枚举口径）；
   - `409` → 状态冲突/自我管理限制（预期行为）；
   - `503` → 基础设施失败（模型/向量库不可用），业务事实不变，可重试。
3. 后端终端的日志里若有 `Traceback`，请连同上述请求一起提供。

> 项目当前未实现深色模式）与**无障碍读屏**表现，需要人工主观判断，不在自动化或
> 契约级验证范围内。
