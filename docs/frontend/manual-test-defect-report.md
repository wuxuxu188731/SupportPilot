### 1.1 环境层面的两点说明（非产品缺陷）

1. **同一 origin 的多 tab 共享 `localStorage`**。`supportpilot.auth` 是按 origin 存储的，因此
   同一浏览器无法在两个 tab 内同时保持两个不同账号的登录态。本次测试通过
   `http://127.0.0.1:5173` 与 `http://localhost:5173` **两个不同 origin** 实现了
   `tester01` 与 `tester02` 的并存会话（C-06 / D-06 / F-13 / G-06 依赖此隔离）。
   这是浏览器正常行为，非缺陷。
2. **CDP Proxy 的 `/eval` 接口 POST body 中的非 ASCII 字符会被损坏为 `U+FFFD`**。
   因此本次测试向页面**写入**中文时统一改用 `String.fromCharCode(...)` 传递；
   从页面**读取**中文不受影响。这是我方测试工具的限值，非被测系统问题。

## 3. 缺陷清单

### DEF-01【中】审批详情页时间未做本地时区换算，与列表页相差 8 小时

- **对应用例**：H-06（时间与时区展示）
- **严重级别**：中（用户可见、影响审批时效判断与审计追溯）
- **复现步骤**：
  1. 登录 `tester01`（浏览器时区 `Asia/Shanghai`，GMT+0800）；
  2. 进入「审批中心」，打开任意一条审批详情；
  3. 对比详情页「基本信息 → 创建时间」「版本历史 → 时间」「决定摘要 → 决定时间」
     「Run 状态 → 创建/更新/完成时间」与系统本地时间。
- **实际现象**：详情页上述时间**全部直接透出后端 UTC ISO 字符串**，例如
  `创建时间 | 2026-09-11T02:21:32Z`、`决定时间 | 2026-09-11T02:24:09Z`；
  而同一时刻浏览器本地时间为 `2026/9/11 10:23:43`（GMT+0800）。
  即页面显示比本地时间**早 8 小时**，且未做格式化（保留 `T`/`Z`）。
- **对照证据（口径不一致）**：
  - 审批**列表**页同一记录显示 `10:21`（已正确换算为本地时间）；
  - **成员管理**页「加入时间：2026-09-11 09:59」，对应接口返回 `created_at = 2026-09-11 01:59:10`（UTC），
    换算正确；
  - 仅**审批详情页**未换算。
- **预期结果**（手册 H-06）：时间均按本地时区展示且与操作时刻一致，无「差 8 小时」现象；
  空值显示「—」。
- **影响**：审批人/审计人员会把「创建时间、决定时间」误读为 8 小时前，破坏时效判断与追溯；
  同一系统内两种时间口径并存，降低可信度。
- **定位建议**：审批详情相关组件（`ApprovalDetailView.vue` / `ApprovalVersionTimeline.vue` /
  `RunStatusPanel.vue`）未复用统一的 `formatDateTime`（成员页使用了该工具）。
  建议统一走同一时间格式化函数。

### DEF-02【中】会话设置：空白输入时对话框静默关闭，预期错误提示永远不可见

- **对应用例**：E-10（会话设置 / 系统提示词）
- **严重级别**：中（实际未保存但无任何反馈，用户会误以为保存成功）
- **复现步骤**：
  1. 进入任一会话页，点击「会话设置」；
  2. 在「会话系统提示词」中只输入若干**空格**；
  3. 点击 **「保存」**。
- **实际现象**：**不发任何网络请求、不出现任何 toast、不出现任何错误文案，对话框直接关闭**。
  再次打开设置，内容仍是上一次的有效值（说明本次确实未保存）。
- **预期结果**（手册 E-10）：输入纯空格时不能保存成功（用户应能感知为何未保存）。
- **代码依据**：`frontend/src/components/chat/ConversationSettingsDialog.vue`
  - `submit()` 在空白输入时执行 `errorMessage.value = '系统提示词不能为空'; return`（第 45-48 行），
    该函数返回类型为 `void`；
  - 模板使用 `<n-modal preset="dialog" ... @positive-click="submit">`（第 60-72 行）。
    Naive UI 的 `n-dialog` 在 `positive-click` 回调未返回 `false`/`Promise` 时**立即关闭对话框**，
    因此 `errorMessage` 被赋值后对话框马上卸载，**「系统提示词不能为空」这条提示是死代码**。
- **影响**：用户无法区分「已保存」与「被拒绝」，属静默失败。
- **修复方向**：`submit()` 在空白分支 `return false`（阻止关闭），或改为受控 `:show`
  且仅在保存成功后关闭。
- **对照**：同一用例的**有效输入**路径完全正常 —— 保存返回 `PUT .../system-prompt/ 200`，
  toast「会话系统提示词已保存」，重开显示已保存值。

### DEF-03【低】本地判定登录过期时不展示「登录已过期」提示

- **对应用例**：H-02（401 会话过期统一处理）
- **严重级别**：低（安全行为正确，仅缺提示）
- **复现步骤**：
  1. 将后端 `ACCESS_TOKEN_TTL_SECONDS` 设为 `60` 并重启；
  2. 登录后**等待超过 60 秒**；
  3. 直接**刷新页面**或地址栏跳转到受保护路由（如 `/app/knowledge`）。
- **实际现象**：跳转 URL 为 `/login?redirect=/app/knowledge`，**不带 `reason=expired`**，
  页面仅有普通登录表单，**没有任何「登录已过期」提示**。
  （本地登录态确实已被清除：`localStorage` 中 `supportpilot.auth` 已移除。）
- **对照：服务端 401 路径是正确的** ——
  登录后停留在页面内、等令牌过期再点击「刷新」，请求返回 **401**，此时跳转
  `/login?reason=expired`，并弹出 toast **「登录已过期，请重新登录」**。
- **预期结果**（手册 H-02）：提示「登录已过期」。
- **代码依据**：`frontend/src/main.ts` 中 `reason=expired` **仅由全局 401 回调
  `setUnauthorizedHandler` 写入**（第 35-44 行）；而路由守卫在本地即可判定令牌过期并
  直接 `replace` 到登录页，该路径不携带 `reason`，因此
  `LoginView.vue:76-77` 的 `message.warning('登录已过期，请重新登录')` 不会触发。
- **影响**：页面刷新后"被踢回"登录页的用户得不到任何解释，体验上像被随机登出。
- **修复方向**：路由守卫的本地过期分支同样带上 `query: { reason: 'expired' }`。

### DEF-05【低】手册 A-01 声称的分组标签 `conversations`、`approvals` 实际不存在

- **对应用例**：A-01（后端可访问 / 分组标签）
- **实际现象**：Swagger UI 实际分组标签为：
  `knowledge`、`authentication`、`organizations`、**`退款/补偿审批与Run`**、
  **`创建新会话`**、**`设置会话的系统提示词`**、**`查询会话列表`**、**`查询会话历史消息`**、

### DEF-06【低】手册 D-06 指引的「把管理员改回客服」在界面上不可行

- **对应用例**：D-06（agent 视角：只读）
- **实际现象**：`tester02` 经 D-05 提升为**管理员**后，成员管理页该行的角色下拉
  被**永久禁用**（`n-base-selection--disabled`），无法改回客服；
  但同一行的 **「移除」按钮仍然可用**。
- **代码依据**：`frontend/src/views/MembersView.vue:290`
  `:disabled="membersStore.isRoleUpdating(member.user_id) || member.role === 'admin'"`
  —— 只要该成员已是管理员，下拉即禁用。
- **手册不符点**：D-06 前置条件写「`tester02` 当前角色为**客服**（若已被 D-05 提升，
  请改回客服）」，但 UI **不存在管理员降级路径**。
  （本次测试改用后端 `PATCH .../members/{user_id}/` 接口才把 `tester02` 还原为客服。）
- **附带产品观察**：「提升为管理员」在 UI 上是**单向操作** —— 可移除、不可降级。
  建议明确这是设计意图（并在手册中写明），或补充降级入口。

### DEF-07【低】手册 F-02 的「内容去重」入口写错；跨文档不做内容去重

- **对应用例**：F-02（上传完成但内容重复 / 幂等）
- **实际现象**：按手册 F-02 的步骤，从**「上传文档」**入口再次上传**完全相同内容**的同名文件，
  后端返回 **201** 并创建了**一篇新文档**（新 `document_id = ccd22887-…`），
  并未提示「内容与当前有效版本相同、未创建重复版本」，文档总数 1 → 2。
- **实现真身**：去重逻辑是**文档内版本维度**的 ——
  `app/knowledge/ingestion.py::_resolve_duplicate` 以 `document_id` 为查询范围
  （配合 `(org, document_id, content_hash)` 唯一约束），只有「同一文档内重复上传同一内容」才短路。
- **实测验证（去重功能本身是好的）**：改走**「上传新版本」**入口提交与当前有效版本**完全相同的内容**，
  页面正确提示 **「上传内容与当前有效版本相同，未创建重复版本。」**，
  且版本历史**不新增**条目（仍为 2 条）。
- **结论**：**实现符合设计，是手册 F-02 的入口描述有误**（应指向「上传新版本」）。
- **附带产品风险（建议确认）**：「上传文档」入口**不做跨文档内容去重**，
  同一内容可被重复上传为多个**独立文档并同时参与检索**。
  本次测试中该行为直接导致知识检索命中了「签收后 7 天」与「签收后 15 天」两版互相矛盾的政策，
  Agent 因此判定**证据不足**并拒绝给出结论（详见 E-07 记录）。
  即：重复文档会污染检索证据质量 —— 建议产品侧确认是否需要在「上传文档」入口增加内容级提示。

## 7. 修复优先级建议

| 优先级 | 缺陷 | 理由 |
| --- | --- | --- |
| P1 | **DEF-01** 审批详情时间未换算时区 | 用户可见且影响审批时效判断与审计追溯，同一系统内两种时间口径 |
| P1 | **DEF-02** 会话设置静默关闭、错误提示不可达 | 静默失败：用户无法判断设置是否生效 |
| P2 | **DEF-03** 本地过期无提示 | 体验问题，但安全行为本身正确 |
| P3 | **DEF-04 / DEF-05** 手册接口统计与分组标签不符 | 文档准确性问题（DEF-05 另建议给 `PUT .../system-prompt/` 补 `tags`） |
| P3 | **DEF-06 / DEF-07** 手册与实现不符（管理员降级、去重入口） | 建议修订手册；DEF-07 另建议产品确认「跨文档去重」策略 |
| P4 | **DEF-08** 证据状态枚举值文案 | 文案口径统一 |
