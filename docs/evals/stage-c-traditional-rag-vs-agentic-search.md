# Stage C：传统 RAG 与 Agentic Search 对比

> 历史结果说明：本文记录的是 Planner 与 rerank 优化前的检索实验，不能代表当前版本。
> 当前优化版本的证据召回率为 Baseline 85%、Agentic Search 90.5%。本文保留用于追踪
> 演进过程，不应再据此判断当前两条链路的相对质量。

## 结论

在当前系统和同一批 48 个评测问题下，传统 RAG 明显优于 Agentic Search。

传统 RAG 的证据召回率、检索精确率和完整证据覆盖率均更高，同时延迟更稳定、额外模型调用更少。当前生产环境应继续以传统 RAG 作为默认检索方案；Agentic Search 暂时保留为实验能力，不建议直接替换传统 RAG。

## 评测范围

- 评测问题：48 个
- 对照运行：每个问题分别运行传统 RAG 和 Agentic Search，共 96 个 variant
- 真实依赖：DashScope Embedding、DeepSeek Planner/Assessor、Qdrant
- 完成情况：96/96 完成，0 个基础设施失败
- 安全结果：两种方案均未出现跨租户、禁用文档、非活跃版本或未知身份泄漏

本次评测主要衡量检索证据质量，而不是由独立裁判模型评价最终自然语言答案。因此，文中的“回答效果”主要指答案可获得的证据是否正确、完整和可靠。

## 总体对比

| 指标 | 传统 RAG | Agentic Search | 更优方案 |
|---|---:|---:|---|
| 证据组召回率 | 57/67，85.1% | 23/67，34.3% | 传统 RAG |
| 检索精确率 | 64/200，32.0% | 25/90，27.8% | 传统 RAG |
| 完整证据覆盖率 | 31/40，77.5% | 12/40，30.0% | 传统 RAG |
| 延迟中位数 | 6.17 秒 | 7.81 秒 | 传统 RAG |
| P95 延迟 | 7.31 秒 | 14.27 秒 | 传统 RAG |
| 平均记录 tokens | 657 | 1,435 | 传统 RAG |
| 额外 Planner/Assessor 调用 | 0 | 77 次，平均 1.6 次/问题 | 传统 RAG |
| 安全泄漏 | 0 | 0 | 相同 |
| 预算耗尽 | 0 | 4 | 传统 RAG |

Agentic Search 的总体平均延迟为 6.75 秒，表面上略低于传统 RAG 的 6.87 秒，但该数字受到 15 个 `none` 策略问题的影响：这些问题没有执行检索，其中一部分属于错误的策略判断。只统计实际执行搜索的 33 个 Agentic Search 问题，其平均延迟为 9.42 秒，平均记录 tokens 为 2,014，平均模型调用为 1.88 次。

在 48 个逐题延迟对比中，传统 RAG 在 32 个问题上更快，Agentic Search 在 16 个问题上更快。

## 逐题质量表现

在具备质量评分的 40 个问题中：

- 证据召回率：传统 RAG 胜出 25 次，Agentic Search 胜出 0 次，持平 15 次。
- 检索精确率：传统 RAG 胜出 27 次，Agentic Search 胜出 0 次，持平 13 次。
- 传统 RAG 的 48 个问题均得到 `complete` 检索状态。
- Agentic Search 得到 20 个 `complete`、13 个 `missing` 和 15 个 `not_applicable`。
- Agentic Search 的策略选择符合允许/首选策略的比例为 17/39，即 43.6%。

## 分类结果

| 问题类型 | 传统 RAG 召回率 | Agentic Search 召回率 | 传统 RAG 完整覆盖率 | Agentic Search 完整覆盖率 |
|---|---:|---:|---:|---:|
| 简单政策 | 100.0% | 50.0% | 100.0% | 50.0% |
| 多条件政策 | 81.3% | 40.6% | 58.3% | 16.7% |
| 事实与政策混合 | 78.9% | 10.5% | 66.7% | 16.7% |
| 安全场景 | 100.0% | 50.0% | 100.0% | 50.0% |

Agentic Search 原本应在多条件和事实混合问题上体现多轮规划优势，但当前结果没有体现这一点，尤其是在事实与政策混合问题上差距最大。

## 原因分析

根据运行轨迹和聚合指标，当前 Agentic Search 的主要问题可能位于 Agent 决策链，而不是 Qdrant 或租户隔离层：

1. Planner 有时错误选择 `none`，使本应检索的问题直接没有证据。
2. 查询改写没有稳定提高召回，部分改写可能偏离用户原始问题。
3. Assessor 可能过滤掉已检索到的有效内容，导致最终 citation 为空或证据不完整。
4. 多轮搜索增加了模型调用、tokens 和尾部延迟，但没有稳定转化为更高的证据覆盖率。
5. 当前语料规模较小且政策表达相对明确，单次混合检索已经具备较强效果，额外的 Agent 决策复杂度暂未产生收益。

以上原因是基于评测结果和运行轨迹作出的工程推断，需要通过针对 Planner、查询改写和 Assessor 的分层实验进一步确认。

## 对回答效果的影响

本次评测没有直接对最终生成文案的语言质量打分，但最终回答的正确性依赖检索证据。传统 RAG 在召回率和完整覆盖率上明显更高，因此更可能生成证据完整、有依据且较少遗漏关键条件的回答。

当前 Agentic Search 更容易出现以下问题：

- 错误判断为不需要搜索；
- 没有找到任何证据；
- 只找到部分必要条件；
- 为获得较少证据消耗更多模型调用和时间。

因此，在当前实现下，传统 RAG 的预期回答可靠性更高。

## 建议

### 当前生产策略

1. 默认继续使用传统 RAG。
2. 不将当前 Agentic Search 直接替换为生产默认方案。
3. 保留 Agentic Search 的功能开关和评测链路，用于后续定向优化。

### Agentic Search 优化优先级

1. 优先修正 Planner 的 `none`、`single`、`multi` 决策，特别是错误选择 `none` 的情况。
2. 对原始查询和改写查询做逐题消融实验，确认哪些改写真正提高召回。
3. 检查 Assessor 是否错误丢弃有效 citation，并记录过滤前后的证据变化。
4. 仅在明确需要拆解的复杂问题上启用多轮检索，简单问题直接走传统 RAG。
5. 优化后继续使用同一批黄金问题回归，至少达到以下条件再考虑扩大使用范围：
   - 召回率和完整覆盖率不低于传统 RAG；
   - 复杂问题上存在可重复的质量提升；
   - P95 延迟和模型调用成本处于可接受范围；
   - 所有租户隔离和预算硬限制继续保持零违规。

### 推荐的演进方向

更现实的短期方案是采用混合路由：默认使用传统 RAG，只有被可靠识别为复杂、多条件或需要跨文档组合的问题才进入 Agentic Search。这样可以保留 Agentic Search 的潜在能力，同时避免所有请求承担额外延迟、模型费用和错误决策风险。
