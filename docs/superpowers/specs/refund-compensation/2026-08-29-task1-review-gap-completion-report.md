## 2. 审查结论回顾

Task 1 的初始实现已经具备领域枚举、实体、异常、Store Protocol、九张业务表、基础复合外键、唯一约束和迁移测试，但代码审查确认仍有以下缺口：

1. 0011 降级会无条件删除动作工作流业务表，已存在的提案、审批、执行和审计事实可能被静默丢弃。
2. 提案版本和审批决定只在应用语义上声明不可变，数据库仍允许直接更新或删除。
3. 同一企业内可以把 Run、提案、版本、审批、执行记录和业务结果错误拼接，原约束只能阻止跨租户引用，不能保证完整授权链属于同一提案。
4. `ActionStore` Protocol 缺少工作流状态转换、按版本读取执行记录和追加恢复审计的契约，无法完整支撑后续确定性工作流节点。
5. 迁移测试未单独覆盖从 0010 升级、有数据降级拒绝、版本不可变及同租户错误引用链。

## 3. 已补齐内容

### 3.1 降级数据保护

在 0011 的 `downgrade()` 开始阶段增加九张动作工作流表的数据检查：

- 任一表存在业务记录时立即拒绝降级；
- 拒绝发生在删除索引或数据表之前；
- 数据库继续停留在 0011，已有业务事实保持可查询；
- 只有九张表全部为空时，才允许对称回滚到 0010。

这使迁移行为符合“存在不兼容数据时 downgrade 明确失败”的设计要求。

### 3.2 不可变业务事实

增加 SQLite 触发器保护以下历史事实：

- `action_proposal_versions` 禁止更新和删除；
- `approval_decisions` 禁止更新和删除；
- 提案的企业、Run、订单、动作类型和创建人等身份字段禁止修改；
- 审批请求的企业、提案、请求版本和请求人等身份字段禁止修改；
- 执行记录的企业、提案、版本、动作类型和幂等键等身份字段禁止修改。

提案的 `current_version_id` 仍允许从版本 1 前进到修改后批准产生的新版本，但不允许清空，也不允许指向其他提案的版本。

### 3.3 同提案引用链完整性

由于 SQLite 建表顺序和 Run/Proposal 双向关系不适合直接使用普通循环外键，本次通过数据库触发器补齐以下约束：

- Proposal 的 `action_type` 必须与 Run 的 `workflow_type` 一致；
- Run 的 `proposal_id` 必须指向同企业、同 Run、同动作类型的提案；
- Proposal 的 `current_version_id` 必须指向该提案自己的版本；
- Approval 的 `requested_version_id` 必须属于该 Approval 对应的提案；
- Approval Decision 的 `decided_version_id` 必须属于该审批对应的提案；
- Tool Execution 的版本必须属于其提案，且执行动作类型必须与提案一致；
- Refund Record 和 Compensation Record 必须与订单、提案、版本和执行记录形成同一条引用链；
- 模拟业务结果的金额、币种和原因码必须与批准版本一致。

这些约束不能替代 Task 2 和 Task 4 的事务重验，但可以阻止同租户数据被错误拼接成看似有效的审批授权链。

### 3.4 Store Protocol 完善

在 `ActionStore` 中新增以下契约：

- `transition_run()`：按预期状态集合原子转换 Run 状态，并同时写入状态审计；
- `get_execution_by_version()`：按提案版本读取稳定执行记录，支持状态查询与重放读取；
- `append_audit_log()`：记录不伴随状态变化的事件，例如管理员显式恢复请求。

`transition_run()` 同时携带稳定错误码、可重试标记、审计主体和详情，使后续 Store 实现能够在同一事务中完成状态变化与审计落库，避免二者分离。

## 4. 新增和调整的测试

本次增加了以下保护场景：

- 提案版本不能更新或删除；
- 提案当前版本不能串用同企业其他提案的版本；
- 审批和执行不能引用其他提案的版本；
- 提案动作类型必须匹配 Run 工作流类型；
- 审批决定不能更新或删除；
- 退款业务结果必须匹配批准版本的金额和完整引用链；
- 数据库可以从 0010 显式升级到 0011；
- 0011 存在业务数据时拒绝降级并保留原数据。

同时修正了原补偿约束测试的构造数据，使补偿版本原因码与补偿结果原因码保持一致，避免测试数据本身违反新增的完整引用链约束。

## 6. 对后续任务的影响

- Task 2 实现 SQLite Store 时，应严格实现新增的三个 Protocol 方法，并在 `BEGIN IMMEDIATE` 事务内落实状态转换与审计原子性。
- Task 2 不应提供修改或删除提案版本、审批决定的 Store 方法。
- Task 3 修改后批准时必须创建下一版本，再更新 `current_version_id`，不能覆盖原版本。
- Task 4 执行器仍需按设计重新读取并验证完整批准链；数据库触发器只是最终防线，不能代替执行前授权校验。
- 生产或共享环境如需从 0011 降级，必须先制定显式的数据导出或清理方案，迁移不会自动丢弃业务事实。
