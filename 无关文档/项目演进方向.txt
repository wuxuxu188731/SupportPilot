智能客服工单agent

它解决的核心问题是：
客服收到客户的自然语言诉求后，需要在订单、物流、售后政策和工单系统之间反复查询、判断、填写和回复。SupportPilot 帮助客服把这段非结构化诉求，转换成有事实依据、可执行、可审批、可追溯的工单处理结果。

这个agent的两类用户有：
1.user :登录SupportPilot的企业员工，例如客服、主管、管理员
2.customers: 向企业咨询、投诉、申请售后的消费者，通常不登录SupportPilot
所以典型的关系是：
```mermaid
flowchart LR
    C["消费者 Customer"] -->|"提出售后问题"| S["客服人员 User"]
    S -->|"在工作台输入问题"| A["SupportPilot Agent"]
    A --> O["查询订单/物流"]
    A --> K["查询售后政策"]
    A --> T["创建或更新工单"]
    A --> R["生成回复草稿"]
    A --> P["发起退款审批"]
    P --> M["主管审批"]
```

它要解决哪些实际问题
真实客服工作通常存在五个问题：
信息分散
客服要分别打开订单、物流、工单、知识库等多个系统。

重复劳动
每次都要复制订单号、总结问题、选择分类、填写工单、编写回复。

处理质量不一致
新客服容易漏问信息、选错分类，或者对同类问题给出不同回答。

高风险操作容易出错
模型或客服不应该因为一句“给他退款”就直接产生退款。

难以追责和复盘
需要知道谁查询了什么、Agent 为什么建议这样处理、最终执行了什么。

SupportPilot 的价值不是“更会聊天”，而是把这些动作串成一个受控闭环。



第一版 MVP 应该做到什么
第一版不要急着做 RAG、LangGraph 和真实退款。只做一个完整、可演示的闭环：
查询订单和物流 → 判断问题类型 → 创建工单 → 生成客服回复。

最低需求可以定义为：
客服登录系统。
客服属于某个企业。
客服提交客户问题。
Agent 能提取订单号和客户诉求。
Agent 能调用 get_order、get_logistics。
Agent 能决定是否创建工单。
Agent 调用 create_ticket。
返回：查询到的事实；
工单编号；
问题分类和优先级；
推荐处理方案；
可直接发送给客户的回复草稿。

所有工具调用都有租户隔离和审计记录。
查询不到信息时明确说明，不编造结果。
一个理想的输出可能是：
订单状态：已付款，尚未出库
物流状态：暂无物流单号
异常判断：超过承诺发货时间 24 小时
已创建工单：T-20260726-001
分类：物流延迟
优先级：中

建议回复：
您好，经查询您的订单目前尚未出库，已经超过预计发货时间。
我们已创建工单 T-20260726-001 跟进处理，预计将在 24 小时内反馈结果。


产品定义：
SupportPilot 是一个面向电商售后客服团队的多租户工单处理 Agent。它能够理解客户诉求，查询订单和物流信息，辅助创建和分类工单，并生成有事实依据的回复；对于退款等高风险操作，系统通过权限、审批、幂等和审计机制保证执行安全。
